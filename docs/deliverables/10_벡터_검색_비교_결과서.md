# 벡터 검색 비교 결과서

작성: 2026-11-01 · 관련 이슈 #31(결과서), #3(도표 조회) · 구현 설명은 [07_AI_시스템_아키텍처.md](07_AI_시스템_아키텍처.md) §6, 시스템 구성은 [09_시스템_구성도.md](09_시스템_구성도.md)

> **이 수치는 보고용이 아니다.** 평가 질의 17건은 개발자가 직접 쓴 초안이라 방향 확인용이다. 질의 1건이 약 6%p 이므로 작은 차이는 의미가 없다. 직접 수집하는 구어체 평가셋(30~50건, #3)이 오면 같은 명령으로 다시 재서 이 문서의 §3 수치를 교체한다.

## 1. 목적과 결론

도표 108개 중 사고 정황에 맞는 도표를 찾는 검색 방식을 정한다. 에이전트는 검색 후보 상위 몇 개를 받아 판단하므로 **정답 도표가 후보 안에 들어오는지(Top-3·Top-5)** 가 가장 중요하고, 1위 적중은 그다음이다.

| 결론 | 근거 |
|---|---|
| **hybrid(키워드+임베딩 순위 결합)를 채택 후보로 한다.** | 후보 3개 안에 정답이 든 비율이 94%(16/17)로 가장 높음. 키워드 71%, 임베딩 76% |
| 임베딩은 "키워드 일치가 약한 구어체"에 강하다. | Top-1 키워드 12% → 임베딩 41% |
| 별도 **벡터DB는 도입하지 않는다.** | 벡터 108개, 파일 약 0.4MB. numpy 코사인으로 한 질의 약 0.2초 |
| 기본 설정(`CHART_SEARCH_MODE`)은 당분간 `keyword` 로 두고, 평가셋 확정 후 `hybrid` 로 바꿀지 정한다. | 임베딩은 모델 약 2GB 와 torch 가 필요하고 최초 로드 약 30초라 배포 부담이 있음 |

## 2. 비교한 방식

| 방식 | 설정값 | 동작 | 의존성 |
|---|---|---|---|
| 키워드 | `keyword` | 한국어 문자 2-gram + IDF 점수 | 없음 |
| 임베딩 | `embedding` | 로컬 KURE-v1(nlpai-lab, bge-m3 기반 한국어 검색 특화, 1024차원) 코사인 유사도 | `requirements-embedding.txt` |
| hybrid | `hybrid` | 위 두 방식의 **순위**를 RRF(k=60)로 결합 | 위와 동일 |

- 색인 텍스트: 도표별 명칭·분류·사고 상황·A/B 설명. 벡터는 `backend/.cache/*.npy` 에 저장(모델명+색인 텍스트 해시로 무효화).
- **폴백**: 임베딩을 쓸 수 없으면(의존성 없음 등) 경고 로그를 남기고 키워드로 자동 대체한다. 단 평가 도구는 이 경우 중단하도록 해 두었다(조용히 키워드로 바뀐 채 비교되면 수치가 왜곡되므로).
- 에이전트의 `search_charts` 도구도 같은 모드를 쓰며, 임베딩 인코딩은 서버 이벤트 루프를 막지 않도록 스레드에서 실행한다.

## 3. 측정 결과 (평가 질의 17건, 2026-11-01 재측정)

평가셋 `backend/eval/chart_search_eval.json`, 실행 `python scripts/eval_chart_search.py -v`. 이전 측정(2026-10)과 수치가 같았다(결정적이므로 당연함).

| 방식 | Top-1 | Top-3 | Top-5 | Top-10 | MRR | 질의당 시간 |
|---|---|---|---|---|---|---|
| 키워드 | 2/17 (12%) | 12/17 (71%) | 14/17 (82%) | 16/17 (94%) | 0.39 | 약 1ms |
| 임베딩 | 7/17 (41%) | 13/17 (76%) | 16/17 (94%) | 16/17 (94%) | 0.62 | 약 210ms |
| hybrid | 7/17 (41%) | **16/17 (94%)** | 16/17 (94%) | 16/17 (94%) | **0.67** | 약 206ms |

- 시간은 로컬 CPU 측정이며 질의 인코딩이 대부분이다. 파이프라인 한 번(약 35~47초)에 비하면 무시할 수 있다.
- **최초 로드**: 임베딩 모델 적재 약 30초(서버 시작 시 미리 로드). 이후 호출에는 영향 없음.
- 임베딩 색인은 108개 도표 × 1024차원 `.npy` 한 개(약 0.4MB).

## 4. 오답 분석

- **어느 방식도 못 찾은 1건(E-01)**: "옆 차선 차가 깜빡이도 없이 갑자기 끼어들어서 부딪혔어요". 정답 차43-2(후행 직진 대 선행 진로변경)가 상위 10위에도 없다. 구어체 "끼어들어서"가 도표 용어 "진로변경"과 어휘가 달라서다. 키워드는 "끼어들기"가 들어간 교차로 동시 우회전 도표(차20-2)를 1위로 골랐고, 임베딩과 hybrid 의 상위 3개도 모두 다른 도표(차32-1, 차18-1, 차55-4 / 차31-4, 차55-2, 차47-1)였다.
- **키워드의 약점**: 정답이 2~4위로 밀리는 질의가 많다(Top-1 12%). 변형 도표가 여럿인 소분류(차2-x, 차16-x 등)에서는 키워드·임베딩 모두 변형끼리 순서가 뒤바뀐다.
- **hybrid 가 임베딩보다 나은 이유**: 임베딩만으로는 Top-3 밖(4위)이던 E-07·E-15·E-16 이 키워드 순위와 결합해 3위 안으로 올라왔다. 반대로 1위가 갈리는 경우(E-02, E-05, E-06…)는 hybrid 도 2위에 머문다.
- **Top-1 은 아직 낮다(41%).** 목표 70%(#3)에 못 미친다. 다만 에이전트가 후보를 받아 도표를 고르는 구조라 후보에 들어오는지(Top-3·5)가 영향이 더 크다.

## 5. 검색 방식이 최종 결과에 미친 영향 (개발용 시나리오 13건)

LLM 비용 없이 `scripts/run_baseline.py` 로 "검색 1위 도표의 기본 비율만 쓰는 포털식" baseline 을 만들어 비교했다(2026-10-21).

| 방식 | 도표 1위 적중 | 정답 범위 적중(naive) | 정답 범위 적중(optimistic) |
|---|---|---|---|
| baseline 키워드 | 23% | 38% | 62% |
| baseline 임베딩 | 54% | 23% | 69% |
| baseline hybrid | 54% | 38% | 85% |
| 본 파이프라인(gpt-4.1) | 100% (위원 중심 도표) | 100% | — |

- naive 는 첫 경우의 A 값을 그대로 쓴다. optimistic 은 역할 반전·경우 선택을 올바로 한다는 느슨한 상한이며 우연히 범위에 드는 것도 적중으로 세므로 파이프라인과의 차이를 **작게** 보이게 한다.
- 파이프라인은 개발용 13건에 맞춰 보정했으므로 보고용 비교가 아니다. 시나리오 세트(#17)로 다시 잰다.
- 이 표의 의미: 검색만으로는(1위만 쓰면) 답이 맞는 경우가 적고, 에이전트가 후보에서 도표를 고르고 가감요소·역할을 적용하는 단계가 정확도에 크게 기여한다.

## 6. 한계

| 한계 | 설명 |
|---|---|
| 평가 질의 17건, 개발자 작성 | 통계적 의미 없음. 표현도 개발자가 아는 도표 용어에 치우칠 수 있음 |
| 정답은 도표 1개만 인정 | 변형 도표가 여럿이면 다른 도표도 사실상 맞을 수 있으나 오답으로 센다(보수적) |
| 모호한 정황 | 후보 점수 근접도로 명백/애매를 구분하지 못했음(D09·D14에서 후보가 흩어짐) → 질문 단계(#26)가 이를 다룬다 |
| 질의 재작성 미측정 | 에이전트가 검색 질의를 도표식으로 바꿔 쓰면 격차가 줄 수 있으나 아직 측정하지 않음 |
| 색인 텍스트 보강 미시도 | 구어체 동의어(끼어들기↔진로변경)를 색인에 넣는 방법은 시도하지 않음 |
| 다른 임베딩 모델 미비교 | KURE-v1 하나만 평가. 다른 모델·크기와의 비교 없음 |
| 벡터DB 미사용 | 규모가 작아 numpy 로 충분. 도표가 수천 장으로 늘면 재검토 |

## 7. 다음 작업

1. 구어체 평가셋(직접 수집, 30~50건)이 오면 같은 명령으로 재측정하고 §3·§4 를 교체한다.
2. Top-1 이 70% 미만이면 (a) 색인 텍스트에 구어체 동의어 보강, (b) LLM 질의 재작성을 차례로 시도하고 각각 같은 평가셋으로 비교한다.
3. 기본 `CHART_SEARCH_MODE` 를 정한다(권장 후보: `hybrid`. 배포 환경에서 모델 용량·로드 시간을 감당할 수 있을 때).

## 8. 재현 방법

```bash
cd backend
python scripts/eval_chart_search.py -v          # 세 방식 비교, 오답 질의 출력
python scripts/eval_chart_search.py --modes keyword,hybrid
python scripts/run_baseline.py                  # 포털식 baseline (LLM 비용 없음)
```

임베딩 사용에는 `pip install -r requirements-embedding.txt` 와 모델 최초 다운로드(약 2GB대)가 필요하다. 평가 질의 파일은 `backend/eval/chart_search_eval.json`.
