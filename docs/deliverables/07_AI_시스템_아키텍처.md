# AI 시스템 아키텍처 (멀티 에이전트 아키텍처)

작성: 2026-10-05 · 구현 상태는 이 시점 기준. 코드 구조 요약은 [ARCHITECTURE.md](../ARCHITECTURE.md) 참고.

> **주 사용자 변경 (2026-10-14):** 사고 당사자용 검증 서비스로 방향을 바꿨다 ([기획서 §9](02_프로젝트_기획서.md)). 아래 에이전트 구조(§1~)는 그대로이고, 앞단에 **결과를 숨긴 사실 질문 단계**, 뒷단에 **범위·조건 리포트와 한계 고지**가 추가될 예정이다 (요구사항 FR-14~16, 질문 생성·검증·사용자용 뷰는 구현 — `core/clarify.py`, `orchestrator.plan_clarification`; 사용자용 API/화면과 실제 모델 측정은 미완). 위원 의견 차이·플래그는 내부/보조 화면용이다.

## 1. 전체 흐름

```
사용자 입력 (AccidentInput)
        │
        ▼
 [기준표 후보 조회]  core/chart_lookup.py  ── 상위 3개 도표를 "힌트"로 생성
        │
        ▼
 1라운드 ┌─────────────┐   ┌─────────────┐   (병렬)
         │ A차량측 에이전트 │   │ B차량측 에이전트 │   ← 도구 호출 루프
         └──────┬──────┘   └──────┬──────┘     search_charts / get_chart
                └───────┬─────────┘
                        ▼
              사실검증 에이전트 (도구 호출 루프, get_chart로 인용 대조)
                        │  flagged_citations
                        ▼
 2라운드  A/B 에이전트 반박 (병렬)
                        │
                        ▼
 검토위원 3종 (병렬, 독립 평가)
   A 기준표 적용 / B 현장 정황 / C 유사사례
                        │
                        ▼
              진행 에이전트 (집계 · 편차 계산 · 리포트)
                        │
                        ▼
        FaultReport: 몇 대 몇 + 근거 + 편차 + "정밀 심사 필요" 플래그
```

## 1-1. 입력과 범위 판별

- 입력(`AccidentInput`)은 자유 서술(`description`, 나=A·상대=B, 10~2000자)이 중심이고 사고 유형·신호·차선·속도는 선택 보조 정보다. 사고 유형 코드 체계는 쓰지 않는다.
- 에이전트 프롬프트에는 파이썬 객체 repr이 아니라 `to_prompt_text()`가 만든 읽기 쉬운 텍스트가 들어간다.
- 파이프라인 시작 시 `core/scope_check.py`가 범위를 판별한다 (LLM 호출 전).
  - 지원: 자동차 대 자동차 (이륜차·긴급자동차 포함)
  - 미지원 → HTTP 422 `out_of_scope` + 안내: 보행자, 자전거, 개인형 이동장치(PM·킥보드), 단독사고
  - 불확실(미지원 키워드와 상대 차량 표현이 함께 있음) → 심사 진행 + `FaultReport.warnings`에 경고
- 한계: 키워드 기반이라 우회 표현은 놓칠 수 있다. 정확도는 시나리오 평가에서 확인한다.

### 검토위원 구조화 출력

- 위원 3종은 공통 부모 `ReviewerAgent`가 `LLMClient.complete_json()`으로 `ReviewerVerdict`를 받는다. 필드는 **생성 순서대로** `checklist → rationale → chart_no → chart_a_is → chart_a_fault → confidence → cited_rules`이다. 정황 A 기준 과실비율 `fault_ratio_a`는 모델이 답하지 않고 **코드가 계산**한다 (`chart_a_is`가 "B"이면 `100 - chart_a_fault`). B 과실은 `100 - A`라 합계가 어긋난 응답이 나올 수 없다.
- **이 구조의 계기 (D03 실측)**: 시나리오 D03(내가 정차 중인 앞차, 도표 차41-1의 B 역할)에서 위원 3명 모두 근거 문장은 "A차량은 과실이 없다"인데 숫자는 A 100(도표 A=뒤차의 값)으로 썼다. 3명이 같은 값을 내 편차 0·플래그 꺼짐이라 **전원 일치 오답이 감지되지 않았다.** 원인으로 의심한 설계 결함 둘: ① 숫자 필드가 스키마 맨 앞이라 모델이 근거보다 먼저 답을 확정함 ② 도표 A→정황 A 변환을 모델의 암산에 맡김. 그래서 숫자를 맨 뒤로 보내고 변환을 코드로 옮겼다. **이 수정의 실제 모델 효과는 아직 측정하지 않았다** (D03/D04 재실행 필요).
- **도표 기본 비율 대조** (`core/verdict_check.py`, LLM 호출 없음): 모델이 답한 도표 A 기준 과실이 해당 도표의 기본 과실(여러 경우면 가장 가까운 경우)에서 40%p 넘게 벗어나거나, 도표번호·역할 대응 필드가 서로 모순되거나, 존재하지 않는 도표번호이면 그 위원의 신뢰도를 low 로 낮추고 경고를 남기며 **위원이 전원 일치해도 "정밀 심사 필요"를 켠다.** 한계: 도표의 A가 정황의 누구인지(`chart_a_is`)를 거꾸로 답하고 숫자도 그에 맞춰 쓰면 이 검사로는 못 잡는다 (역할 판단 자체의 오류는 A/B 에이전트의 대응 명시·사실검증 (5)·위원 간 불일치로 잡아야 한다).
- 스키마를 JSON Schema로 강제하고 응답은 pydantic으로 직접 검증한다. 파싱·범위 검증에 실패하거나 응답이 잘리면 실패 사유를 덧붙여 최대 3회 재시도하고, 그래도 안 되면 `StructuredOutputError`. **거절(refusal)은 재시도하지 않는다.** 이 검증·재시도는 프로바이더와 무관하게 `LLMClient`가 공통으로 처리한다.
  - OpenAI: Responses API의 `text.format`(json_schema, `strict: true`). strict 모드는 모든 필드를 required로 두고 값 범위 제약(min/max 등)을 지원하지 않으므로 `strict_json_schema()`가 pydantic 스키마를 그에 맞게 변환하고, 범위(A 과실 0~100 등)는 응답을 받은 뒤 pydantic이 검증한다.
  - Anthropic: `output_config.format`(json_schema). SDK의 `messages.parse`는 거절처럼 본문이 비면 `stop_reason`을 확인하기 전에 예외를 던져 거절을 재시도하게 되므로 쓰지 않고, `create`로 받은 뒤 직접 검증한다.
- 위원에게는 A/B 논증과 사실검증 결과를 읽기 쉬운 텍스트로 전달하고, "논증은 유리하게 쓴 것이므로 독립 평가", "사실검증 오류 주장은 근거 제외" 규칙을 공통으로 붙인다.
- 신뢰도(`confidence`)는 이후 "정밀 심사 필요" 플래그 산식(#13)과 판례 없는 도표 처리(#10)에 쓴다.

### 검토위원 3종: 관점·근거 자료·체크리스트

| 위원 | 관점 | 받는 근거 자료 | 체크리스트 (요약) |
|---|---|---|---|
| A 기준표 적용 | 기준표를 규정대로 적용 | 인용 도표 상세 (기본 과실, 가감요소, 택일 그룹, 수정요소 해설) | 도표·경우 선택 → 기본 비율 → A측/B측 가감요소(정황에 있는 사실만) → 포털 계산식으로 최종 산정 |
| B 현장 정황 | 현장 조건이 책임에 준 영향 | 인용 도표 상세 | 시야 → 속도 → 예견·반응 가능성 → 신호·표지·차선 → 도로 환경 → 기본 비율 대비 조정폭. **정황에 없는 사실은 추측 금지** |
| C 유사사례 | 비슷한 사고와의 형평성 | 인용 도표 상세 + **판례·조정사례(근거 등급 표시)** | 근거 등급 → 사실관계 유사성 → 사례의 인정 비율 → 차이의 반영 → 형평성 결론. **주어진 사례만 인용** |

- 위원에게 주는 도표는 A/B 논증이 **실제로 인용한 존재하는 도표**(최대 4개)다. 후보 검색 결과가 아니다.
- 공통 규칙: 논증은 유리하게 쓴 것이므로 독립 평가, 사실검증 오류 주장은 근거 제외, 주어진 자료 밖 도표·판례 인용 금지, 항목별 `checklist` 판단 출력.
- **가감요소 계산식**(포털 스크립트로 확인): `A 과실 = 기본 A + (A측 가감점 합) − (B측 가감점 합)`, 0~100. 같은 `[택일N]` 표시의 가감요소는 하나만 적용.
- **판례 근거 등급**: `direct`(인용 도표 자체에 판례) / `similar`(없지만 같은 분류의 유사 도표에 있음, 직접 근거로 쓰지 않도록 표시) / `none`. 원문에 판례가 없는 31개 도표 중 30개가 `similar`, 1개(차46-1 양 차량 유턴)만 `none`이다. `similar`·`none`이면 위원 C는 confidence를 낮춘다.
- **위원 일부 실패 허용**: 위원이 오류로 실패해도 나머지로 진행하고 경고를 남기며, 독립 평가가 줄었으므로 `needs_precise_review`를 켠다. 유효 평가가 2건 미만이면 심사를 중단한다.
- **"정밀 심사 필요" 플래그 산식**: 위원 A과실의 **최대-최소 차이(spread) ≥ 20%p 또는 표준편차 > 15** 이면 켠다 (둘 다 초기값, 평가셋 실측 후 조정, #13). 표준편차만 쓰면 위원이 3명일 때 이상치 한 명을 놓친다 — 한 명이 나머지와 d점 벗어나면 표준편차가 약 0.47×d라서 임계값 15는 d ≥ 32점이 필요하다. 실제 첫 측정에서 위원 A과실이 30/0/0(30점 차)인데 표준편차 14.1로 플래그가 안 켜진 것이 계기다. `FaultReport.spread`로 함께 노출한다.
- 한계: 프롬프트는 아직 시나리오 여러 건으로 검증·튜닝하지 못했다 (#2). 임계값 20·15는 근거 있는 값이 아니라 초기값이다.

## 3. 오케스트레이션 방식

| 구분 | 결정 | 이유 |
|---|---|---|
| 흐름 통제 | 코드 (`FaultAssessmentPipeline`, `asyncio.gather`로 병렬) | 심사 단계가 고정이라 재현성과 디버깅에 유리 |
| 에이전트 간 호출 | 에이전트가 서로를 호출하지 않음 | 파이프라인이 컨텍스트를 전달 |
| 에이전트 내부 | **도구 호출 루프** (논증·사실검증) | 모델이 기준표를 스스로 조회·확인 후 인용 |
| LLM 클라이언트 | `LLMClient` — 프로바이더 선택(`LLM_PROVIDER`: openai 기본 / anthropic), async, 키 없으면 mock. 구조화 출력 검증·재시도는 공통 처리 | 키 없이도 파이프라인 전체 테스트, 프로바이더 교체 가능 |
| 에이전트 구조 | 얇은 에이전트 + 두꺼운 파이프라인 | 에이전트는 `run(context)` 단일 진입점 |

## 4. 도구 (Tool)

| 도구 | 입력 | 출력 |
|---|---|---|
| `search_charts(query, limit)` | 사고 상황 문장 | 후보 도표 목록 (번호, 명칭, 분류) |
| `get_chart(chart_no, include_notes)` | 도표번호 | 기본 과실, 경우별 비율, 가감요소, 관련 법규(, 수정요소 해설) |

존재하지 않는 도표번호를 조회하면 오류 문구를 돌려줘 환각 인용을 에이전트가 스스로 정정할 수 있게 한다.

## 5. 환각 방지 장치

1. 프롬프트: 조회하지 않은 도표번호·비율·조문 인용 금지
2. 도구: 존재하지 않는 도표는 오류 반환
3. **규칙 기반 사전 검증** (`core/citation_check.py`, LLM 호출 없음): 존재하지 않는 도표번호(error), 도표번호 근처에서 주장한 기본 과실비율이 해당 도표의 어떤 경우와도 불일치(error, A:B 뒤집힘은 허용), 인용 법조문이 도표의 관련 법규에 없음(warning)
4. 사실검증 에이전트: 규칙 검증 결과를 받아 도구로 나머지(가감요소 적용 적정성 등)를 확인, 오류를 `flagged_citations`("A측/B측 …", 경고는 "(경고)" 접두어)로 구조화
5. 2라운드: 사실검증 지적을 측별로 나눠 A/B 에이전트에 전달 (자기 측은 정정·철회, 상대 측은 반박 근거로 활용)
6. 추적: 모든 도구 호출을 `AgentArgument.tool_calls`에 기록
7. **역할 대응 규칙**: 도표의 A/B는 도표가 정한 역할 이름이라 정황의 A(나)/B(상대)와 다를 수 있다. 논증·위원·사실검증 프롬프트 모두 `도표 A = 정황 A/B` 대응을 먼저 밝히고 비율을 **정황 A 기준**으로 환산하게 한다 (첫 실제 실행에서 도표 A 비율을 정황 A 비율처럼 써 A 100 으로 오판한 사례에서 도입).
8. **합계 검증(규칙 기반)**: `A xx : B yy` 형태의 비율 쌍의 합이 100이 아니면 error (가감요소를 한쪽에만 더한 "A 30 : B 80"). 프롬프트가 지정한 출력 형식 `최종: 정황 A xx : 정황 B yy`도 잡는다.

한계: 비율 검사는 도표번호 뒤 60자 안의 `숫자:숫자` 표기만 본다. 표기를 달리하면 놓칠 수 있다(오탐보다 미탐을 택한 설계).

## 6. 기준표 조회 (RAG에 해당하는 부분)

색인 텍스트는 도표별 명칭·분류·사고 상황·A/B 설명이다. 검색 방식은 설정 `CHART_SEARCH_MODE`로 고른다.

| 모드 | 방식 | 의존성 |
|---|---|---|
| `keyword` (기본) | 한국어 문자 2-gram + IDF | 없음 |
| `embedding` | 로컬 **KURE-v1**(nlpai-lab, bge-m3 기반 한국어 검색 특화, 1024차원) 코사인 유사도. 벡터는 디스크에 캐시(모델명+색인 텍스트 해시로 무효화) | `requirements-embedding.txt` (torch CPU, sentence-transformers, 모델 약 2GB대) |
| `hybrid` | keyword와 embedding의 **순위**를 RRF(k=60)로 결합 | 위와 동일 |

- 임베딩을 쓸 수 없으면(의존성 없음 등) 경고 로그 후 keyword로 자동 대체된다. 임베딩 모드면 서버 시작 시 모델을 미리 로드한다.
- 벡터 108개라 별도 벡터DB 없이 numpy 코사인으로 충분하다 (벡터DB 도입 여부는 산출물 요건과 의존성 비용을 따져 결정).
- 에이전트의 `search_charts` 도구도 같은 모드를 쓰며, 임베딩 인코딩은 이벤트 루프를 막지 않도록 스레드로 실행한다.

**초기 비교 (개발용 초안 17건, 개발자가 작성 — 방향 확인용이며 보고용 수치가 아님)**

| 모드 | Top-1 | Top-3 | MRR |
|---|---|---|---|
| keyword | 12% | 71% | 0.39 |
| embedding (KURE-v1) | 41% | 76% | 0.62 |
| hybrid | 41% | 94% | 0.67 |

- 에이전트에 후보 3개를 넣는 구조에서는 Top-3가 핵심이라 hybrid가 가장 유리해 보인다. Top-1은 아직 낮다 (목표 70%, #3).
- 이전에 "1위 적중 약 절반"이라고 적었던 수치는 도표 용어에 가깝게 쓴 질의 8건으로 잰 값이라 낙관적이었다. 구어체 질의로는 keyword Top-1이 12%다.
- 약점: "끼어들었다" 같은 구어체와 도표 명칭("선행 진로변경")의 어휘 차이 (예: E-01은 embedding 상위 10위에도 없음). 에이전트가 도구로 검색할 때는 스스로 도표식 표현으로 질의를 바꿔 쓰므로 이 격차가 다소 줄 수 있으나 아직 측정하지 않았다.
- **다음**: 직접 수집하는 30~50개 구어체 평가셋으로 재측정(`python scripts/eval_chart_search.py -v`), 색인 텍스트 보강·질의 재작성(LLM) 시도. 평가셋 최종본 수치를 보고서에 사용한다.

## 7-1. 시나리오 일괄 평가 도구

`backend/scripts/run_scenarios.py` (로직은 `app/evaluation/scenarios.py`, 이슈 #2 튜닝·#18 최종 평가 공용). 시나리오 파일을 읽어 파이프라인을 시나리오마다 새로 만들어 실행하고 정답과 비교한다.

| 지표 | 정의 |
|---|---|
| 도표(주) | 검토위원이 가장 많이 언급한 도표가 정답 도표 중 하나인가 (최종 판단이 기댄 도표) |
| 도표(any) | 정답 도표가 위원 텍스트 어디에든 언급됐는가 |
| 범위 | 최종 A 과실이 정답 범위(`expected_ratio_a`) 안인가 — 명백 시나리오의 핵심 지표 |
| 애매 플래그 | 애매 시나리오에서 "정밀 심사 필요" 플래그가 켜진 비율 — 애매 시나리오의 핵심 지표 |
| 호출·토큰 | 시나리오별 LLM 호출 수와 입력/출력 토큰 (`LLMClient.usage`; 재시도·도구 루프의 매 호출 포함). 단가를 `--price-in/--price-out`으로 주면 비용 계산 (**가격은 코드에 고정하지 않음**) |

- 모델·검색 모드·추론 강도를 바꿔 같은 세트를 돌리고 비교표를 출력한다 (`--models`, `--search-mode`, `--reasoning-effort`).
- 안전장치: `--dry-run`(호출 없음), 키 없는 mock 모드 거부(`--allow-mock`), 시나리오마다 즉시 저장 + `--resume`, mock 결과는 라벨·파일명(`_MOCK`)을 분리해 실제 결과와 섞이지 않음, 한 시나리오의 실패(범위 밖 거절·구조화 실패 등)는 오류 결과로 기록하고 계속 진행. 결과는 `eval/results/`(git 제외).
- 시나리오 파일 검증: id 중복, 존재하지 않는 정답 도표(오타), 정답 범위 형식 오류를 실행 전에 거른다.
- `eval/scenarios_dev.json`: 개발용 13건(개발자 작성). **도표의 A/B 역할이 같은 경우와 반전된 경우를 쌍으로** 넣어 역할 대응 오류를 측정한다. 정답 범위는 도표 기본 비율에서 계산한 값(±10)이며 가감요소 적용 여부는 반영하지 않았다. 보고용 수치가 아니다.

  - **D03/D04 실측 (2026-10-05, `gpt-4o-mini`, keyword)**: 둘 다 도표는 정답(차41-1). **D03(도표의 B 역할)은 위원 3명 전원이 A 100으로 오답**(정답 0~10), D04(도표의 A 역할)는 A 100으로 정답. 입력 156,907 / 출력 8,299 토큰, 호출 33회(시나리오당 16~17회), 평균 36초. 위 "이 구조의 계기" 참고.

  - **오답 6건 재실행과 `scene_a_fault` 도입 (2026-10-05, `gpt-4.1`)**: 6건 중 2건(D09, D13)만 정답 범위. 위원 원답을 저장해 보니 오답·의심 위원 답 9개 중 6개가 **역할(`도표 A=정황 B`)은 맞게 답하고 숫자 칸에 정황 A 기준 값을 적어 코드가 한 번 더 뒤집는 이중 변환**(D02 2, D06 1, D08 1, D10 2), 3개는 역할 반전을 못 한 오류(D06 2, D08 1)였다. 근거 문장에는 정황 기준 값이 맞게 적혀 있어, 위원이 **정황 A 기준 과실 `scene_a_fault`를 직접 답하고**(최종값) 코드는 `chart_a_is`로 도표 기본 비율을 정황 기준으로 바꿔 대조만 한다(`verdict_check`: 40%p 초과 시 신뢰도 low·경고·정밀 심사 플래그). 1차로 도표 기준 값(`chart_a_fault`)도 함께 받아 교차 검증했더니 6건 모두 정답 범위(오답이던 6건 재실행, 위원 전원 일치)였지만 모델이 도표 쪽 칸에 정황 값을 적어 정답에도 불일치 경고가 붙어(D02·D06·D08·D13) 도표 기준 칸은 제거했다. 역할 반전을 못 한 유형은 이 검증으로 잡히지 않는다.
  - **단계별 13건 비교 (2026-10-14, 개발용·`gpt-4.1` 기준)**: ① mini·평균·도표 기준 값 7/13 → ② 4.1 동일 구조 7/13 → ③ `scene_a_fault` 12/13 → ④⑤ 가감요소 인용 규칙 추가 후 13/13 (반복 2회 모두, 최종값은 4건이 10%p 변동). 개발용 세트에 맞춰 고친 결과라 보고용 수치가 아니다. 애매 사례 D09(도표 2개 가능)는 위원 숫자가 일치하면 플래그가 안 켜지는 문제가 남아, **위원 `confidence`가 low인 위원이 2명 이상이면 정밀 심사 플래그**를 추가하고(`LOW_CONFIDENCE_REVIEWERS=2`, 초기값·미보정) 플래그 사유를 `FaultReport.flag_reasons`로 남긴다. 평가 결과에 위원별 확신을 저장해 실행 후 기준을 조정한다. 실측(13건)에서 gpt-4.1은 확신 39개 중 high 35·medium 4·low 0으로 거의 항상 high라 이 규칙은 한 번도 작동하지 않았다 — 모델의 자기 확신은 모호함을 반영하지 않는다. 대신 **위원이 서로 다른 도표를 적용하면 플래그**를 추가했다(저장된 gpt-4.1 실행 64건 중 불일치는 애매 사례 D09 3건뿐, 명백한 사례 오탐 0건; D09 6회 중 플래그 3회→5회). A/B 에이전트가 서로 다른 도표를 주장하는 경우는 적대적 구조상 흔해 신호로 쓰지 않았다.
  - **D01 결과**: 도표는 정답(차43-2)이나 최종 A 10 (개발용 정답 범위 20~40 밖). 위원 A과실이 기준표 30 / 현장 정황 0 / 유사사례 0. 범위 밖 판정은 개발용 범위가 가감요소를 반영하지 않은 한계일 수 있어(B 신호불이행 +10 → A 20, 추가 가산이 근거 있으면 더 낮아짐) 위원 근거를 확인해야 한다 (이번 결과 파일에는 위원 근거가 저장되지 않았음 — 이후 실행부터 저장).
- 위원·진행 에이전트는 도구 없는 단발 호출이다. 구조화 출력 파싱은 #7.
- 모델 응답 거절(`refusal`) 시 예외로 처리한다. 폴백 모델 설정은 두지 않았다.
