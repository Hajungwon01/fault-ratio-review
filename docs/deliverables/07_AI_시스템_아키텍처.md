# AI 시스템 아키텍처 (멀티 에이전트 아키텍처)

작성: 2026-10-05 · 구현 상태는 이 시점 기준. 코드 구조 요약은 [ARCHITECTURE.md](../ARCHITECTURE.md) 참고.

## 1. 전체 흐름

```
사용자 입력 (AccidentInput)
        │
        ▼
 [기준표 후보 조회]  core/chart_lookup.py  ── 상위 3개 도표를 "힌트"로 생성
        │
        ▼
 1라운드 ┌─────────────┐   ┌─────────────┐   (병렬)
         │ A차량측 에이전트 │   │ B차량측 에이전트 │   ← Tool Runner 루프
         └──────┬──────┘   └──────┬──────┘     search_charts / get_chart
                └───────┬─────────┘
                        ▼
              사실검증 에이전트 (Tool Runner, get_chart로 인용 대조)
                        │  flagged_citations
                        ▼
 2라운드  A/B 에이전트 반박 (병렬)
                        │
                        ▼
 검토위원 3종 (병렬, 독립 평가)
   A 기준표 적용 / B 현장 정황 / C 유사사례
                        │
                        ▼
              진행 에이전트 (집계 · 편차 계산 · 리포트)
                        │
                        ▼
        FaultReport: 몇 대 몇 + 근거 + 편차 + "정밀 심사 필요" 플래그
```

## 1-1. 입력과 범위 판별

- 입력(`AccidentInput`)은 자유 서술(`description`, 나=A·상대=B, 10~2000자)이 중심이고 사고 유형·신호·차선·속도는 선택 보조 정보다. 사고 유형 코드 체계는 쓰지 않는다.
- 에이전트 프롬프트에는 파이썬 객체 repr이 아니라 `to_prompt_text()`가 만든 읽기 쉬운 텍스트가 들어간다.
- 파이프라인 시작 시 `core/scope_check.py`가 범위를 판별한다 (LLM 호출 전).
  - 지원: 자동차 대 자동차 (이륜차·긴급자동차 포함)
  - 미지원 → HTTP 422 `out_of_scope` + 안내: 보행자, 자전거, 개인형 이동장치(PM·킥보드), 단독사고
  - 불확실(미지원 키워드와 상대 차량 표현이 함께 있음) → 심사 진행 + `FaultReport.warnings`에 경고
- 한계: 키워드 기반이라 우회 표현은 놓칠 수 있다. 정확도는 시나리오 평가에서 확인한다.

## 2. 에이전트 구성

| # | 에이전트 | 클래스 | 입력 | 출력 | 도구 | 상태 |
|---|---|---|---|---|---|---|
| 1 | A차량측 | `VehicleAAgent` (`AdvocateAgent`) | 정황, 후보 도표, 상대 주장 | `AgentArgument` (+인용, 도구 호출 기록) | search_charts, get_chart | 구현 (실제 API 미검증) |
| 2 | B차량측 | `VehicleBAgent` (`AdvocateAgent`) | 〃 | 〃 | 〃 | 〃 |
| 3 | 사실검증 | `FactCheckerAgent` | 양측 주장, 정황, 후보 도표 | `FactCheckResult` (오류 구조화) | get_chart 등 | 구현 |
| 4 | 위원 A (기준표) | `ReviewerStandardAgent` | 정황, 논증, 검증 결과 | `ReviewScore` (비율·신뢰도·인용) | 없음 | 파싱 공통화 완료, 관점별 프롬프트는 스텁 (#8) |
| 5 | 위원 B (현장 정황) | `ReviewerSceneAgent` | 〃 | 〃 | 없음 | 파싱 공통화 완료, 관점별 프롬프트는 스텁 (#9) |
| 6 | 위원 C (유사사례) | `ReviewerPrecedentAgent` | 〃 | 〃 | 없음 | 파싱 공통화 완료, 관점별 프롬프트는 스텁 (#10) |
| 7 | 진행 | `ProceedingAgent` | 위원 평가, 라운드 기록 | `FaultReport` | 없음 | 스텁 (#12, #13) |

### 검토위원 구조화 출력

- 위원 3종은 공통 부모 `ReviewerAgent`가 `LLMClient.complete_json()`으로 `ReviewerVerdict`(A 과실비율 0~100 정수, 신뢰도 high/medium/low, 근거, 인용)를 받는다. B 과실은 `100 - A`로 계산해 합계가 어긋난 응답이 나올 수 없다.
- 스키마는 `output_config.format`(json_schema)으로 강제하고, 응답은 pydantic으로 직접 검증한다. 파싱·범위 검증에 실패하면 실패 사유를 덧붙여 최대 3회 재시도하고, 그래도 안 되면 `StructuredOutputError`. **거절(refusal)은 재시도하지 않는다.**
  (SDK의 `messages.parse`는 거절처럼 본문이 비면 `stop_reason`을 확인하기 전에 예외를 던져 거절을 재시도하게 되므로 쓰지 않았다.)
- 위원에게는 A/B 논증과 사실검증 결과를 읽기 쉬운 텍스트로 전달하고, "논증은 유리하게 쓴 것이므로 독립 평가", "사실검증 오류 주장은 근거 제외" 규칙을 공통으로 붙인다.
- 신뢰도(`confidence`)는 이후 "정밀 심사 필요" 플래그 산식(#13)과 판례 없는 도표 처리(#10)에 쓴다.

## 3. 오케스트레이션 방식

| 구분 | 결정 | 이유 |
|---|---|---|
| 흐름 통제 | 코드 (`FaultAssessmentPipeline`, `asyncio.gather`로 병렬) | 심사 단계가 고정이라 재현성과 디버깅에 유리 |
| 에이전트 간 호출 | 에이전트가 서로를 호출하지 않음 | 파이프라인이 컨텍스트를 전달 |
| 에이전트 내부 | **Tool Runner 루프** (논증·사실검증) | 모델이 기준표를 스스로 조회·확인 후 인용 |
| LLM 클라이언트 | `LLMClient` (async, API 키 없으면 mock) | 키 없이도 파이프라인 전체 테스트 |
| 에이전트 구조 | 얇은 에이전트 + 두꺼운 파이프라인 | 에이전트는 `run(context)` 단일 진입점 |

## 4. 도구 (Tool)

| 도구 | 입력 | 출력 |
|---|---|---|
| `search_charts(query, limit)` | 사고 상황 문장 | 후보 도표 목록 (번호, 명칭, 분류) |
| `get_chart(chart_no, include_notes)` | 도표번호 | 기본 과실, 경우별 비율, 가감요소, 관련 법규(, 수정요소 해설) |

존재하지 않는 도표번호를 조회하면 오류 문구를 돌려줘 환각 인용을 에이전트가 스스로 정정할 수 있게 한다.

## 5. 환각 방지 장치

1. 프롬프트: 조회하지 않은 도표번호·비율·조문 인용 금지
2. 도구: 존재하지 않는 도표는 오류 반환
3. **규칙 기반 사전 검증** (`core/citation_check.py`, LLM 호출 없음): 존재하지 않는 도표번호(error), 도표번호 근처에서 주장한 기본 과실비율이 해당 도표의 어떤 경우와도 불일치(error, A:B 뒤집힘은 허용), 인용 법조문이 도표의 관련 법규에 없음(warning)
4. 사실검증 에이전트: 규칙 검증 결과를 받아 도구로 나머지(가감요소 적용 적정성 등)를 확인, 오류를 `flagged_citations`("A측/B측 …", 경고는 "(경고)" 접두어)로 구조화
5. 2라운드: 사실검증 지적을 측별로 나눠 A/B 에이전트에 전달 (자기 측은 정정·철회, 상대 측은 반박 근거로 활용)
6. 추적: 모든 도구 호출을 `AgentArgument.tool_calls`에 기록

한계: 비율 검사는 도표번호 뒤 60자 안의 `숫자:숫자` 표기만 본다. 표기를 달리하면 놓칠 수 있다(오탐보다 미탐을 택한 설계).

## 6. 기준표 조회 (RAG에 해당하는 부분)

- 현재: 도표별 텍스트(명칭, 분류, 사고 상황, A/B 설명)를 한국어 문자 2-gram + IDF로 점수화하는 키워드 검색
- 실험 결과: 5개 시나리오 모두 상위 3개 후보 안에 정답 도표 포함. 1위 적중은 수동 점검 8건 중 약 절반
- 예정: 임베딩 기반 검색과 정확도 비교 (#3). 도입 여부는 비교 결과로 결정

## 7. 기술 스택

| 영역 | 기술 |
|---|---|
| 백엔드 | Python 3.12, FastAPI, Pydantic |
| LLM | Anthropic API (기본 `claude-opus-5-5`, `LLM_MODEL`로 변경), SDK 1.x Tool Runner |
| 프론트엔드 | 순수 HTML/JS (빌드 도구 없음) |
| 테스트 | pytest (루프 배선은 `httpx2.MockTransport`로 가짜 `/v1/messages` 서버 사용) |
| 개발 환경 | PyCharm 공유 Run Configuration, GitHub Project 관리 |

## 8. 미정/리스크

- 실제 API로 도구 호출 횟수·지연·비용을 아직 측정하지 않았다 (#1). 에이전트 7개가 도구 루프를 돌면 호출 수가 늘어난다.
- 위원·진행 에이전트는 도구 없는 단발 호출이다. 구조화 출력 파싱은 #7.
- 모델 응답 거절(`refusal`) 시 예외로 처리한다. 폴백 모델 설정은 두지 않았다.
