# 사용자용 API 설계 (사고 당사자 흐름)

상태: **1차 구현됨** (결정: 답변 반영 A=`resolve()`, 세션 메모리+30분, 내부 `/assess`는 `INTERNAL_API_ENABLED`로 끔) · 작성·구현 2026-10-15
구현: `app/models/user_schemas.py`, `app/core/sessions.py`, `app/core/user_flow.py`, `app/main.py` · 테스트: `tests/test_user_api.py` · 실제 모델로는 아직 질문 흐름을 검증하지 못함(질문이 생성된 실측 사례 없음) · 관련 요구사항: FR-14~16 ([03_요구사항_정의서.md](deliverables/03_요구사항_정의서.md))

## 1. 왜 따로 만드나

지금 `POST /assess`는 `FaultReport` 전체를 돌려준다. 여기에는 **보기별 도표·과실(`clarifications`), 위원별 의견, 플래그 사유**가 들어 있어서, 그대로 사용자에게 보여 주면 질문 단계의 "결과 숨김" 원칙이 무너진다 (사용자가 유리한 답을 고를 수 있다).
그래서 사용자용 API는 **서버가 전체 결과를 쥐고 있고, 사용자에게는 단계별로 안전한 부분만 내보낸다.** 기존 `/assess`는 개발·평가용 내부 API로 남긴다.

## 2. 흐름

```
 사용자                     서버
   │  POST /v1/assess              (사고 정황)
   │ ────────────────────────────▶ 파이프라인 실행 → FaultReport(내부) 를 세션에 보관
   │ ◀──────────────────────────── ① 질문이 필요 없음 → status=done + 결과(범위·조건·증거·고지)
   │                                ② 질문이 필요함   → status=needs_answer + session_id + 질문(결과 숨김)
   │  POST /v1/assess/{id}/answer  (보기 id, 또는 모름)
   │ ────────────────────────────▶ resolve() 로 답변 반영, 세션 종료
   │ ◀──────────────────────────── status=done + 결과 ("사용자 진술 기준" 표기)
```

- 질문은 **최대 1개**, 답변은 **세션당 1회** (같은 세션에서 보기를 바꿔 가며 결과를 비교하지 못하게 한다).
- 사용자에게 처음 보이는 것은 정황 입력 결과 대신 **질문**이다. 과실비율·도표번호는 답변 뒤에만 나온다.

## 3. 엔드포인트

| 메서드 | 경로 | 요청 | 응답 | 공개 |
|---|---|---|---|---|
| POST | `/v1/assess` | `AccidentInput` | `AssessResponse` | 사용자 |
| POST | `/v1/assess/{session_id}/answer` | `AnswerRequest` | `AssessResponse` (done) | 사용자 |
| GET | `/health` | - | 상태 | 공개 |
| POST | `/assess` | `AccidentInput` | `FaultReport` 전체 | **내부/개발용** (운영에서는 설정으로 끈다) |

### 응답 형태

```jsonc
// 질문이 필요한 경우 — 도표번호·과실·증거·플래그 없음
{
  "status": "needs_answer",
  "session_id": "b1f0...",            // 추측할 수 없는 무작위 토큰
  "expires_in_sec": 1800,
  "question": {
    "seed": 123456789,                  // 보기 순서 섞기용, 답변 때 되돌려 보낸다
    "text": "충돌 직전 내 방향과 상대 방향의 신호는 각각 무엇이었나요?",
    "options": [
      {"id": 0, "label": "..."}, {"id": 1, "label": "..."}, {"id": -1, "label": "모름 / 확실하지 않음"}
    ]
  },
  "notice": "..."                       // 한계 고지
}

// 답변 요청
{ "option_id": 1, "seed": 123456789 }   // 모름: option_id = -1 (또는 null)

// 결과
{
  "status": "done",
  "result": {
    "my_fault_low": 0, "my_fault_high": 10,        // 나의 과실 범위 (정황 A 기준). 단정하지 않는다
    "other_fault_low": 90, "other_fault_high": 100,
    "assumption": "사용자 진술 기준: ... (사실로 확인된 것이 아닙니다)",   // 질문에 답했을 때만
    "explanation": "...",                           // 적용 도표·가감요소·근거 (법규 인용 포함)
    "charts": [{"chart_no": "차2-2", "title": "..."}],   // 답변 뒤에는 공개
    "evidence_to_check": ["블랙박스 영상", "신호 주기 기록"],
    "other_possibilities": "...",                   // 질문하지 않은 경우의 참고 문구 (clarification_note)
    "uncertain": true,                              // 위원 의견이 갈렸으면 true → "전문가 확인 권장" 문구
    "disclaimer": "참고용이며 법적 효력이 없습니다. 최종 판단은 보험사, 과실비율분쟁심의위원회, 법원에 있습니다."
  }
}
```

### 결과 범위(`my_fault_low/high`) 계산 규칙

| 상황 | 범위 |
|---|---|
| 질문 없음 | 위원 3명의 정황 A 과실 최소~최대 (일치하면 한 값) |
| 보기를 고름 | 고른 보기의 값 (진술 기준) |
| 모름 | 모든 보기 값의 최소~최대 |

## 4. 사용자에게 절대 내보내지 않는 것

`clarifications`의 보기별 `chart_no`/`scene_a_fault`/`evidence`(질문 단계), 위원별 의견·확신·도표, `flag_reasons`, `rounds`(양측 논증 전문), 내부 경고(`warnings`) 원문. 사용자 응답은 위 스키마로만 만들고 `FaultReport`를 그대로 직렬화하지 않는다 (테스트로 키 집합을 고정한다).

## 5. 세션 보관

| 방식 | 장점 | 단점 |
|---|---|---|
| **서버 메모리 + TTL(30분)** (권장, 1차) | 구현이 가장 단순, 내부 데이터가 서버 밖으로 안 나감 | 서버 재시작 시 세션 소멸, 프로세스 1개만 지원 |
| 암호화 토큰(상태 비저장) | 서버 상태 없음 | 암호 라이브러리 추가, 토큰 크기, 키 관리 |
| DB(Redis/SQLite) | 재시작·다중 프로세스 가능 | 학생 프로젝트 범위에서는 과함 |

세션은 답변 1회 후 삭제, 만료 시 삭제, 최대 동시 세션 수 제한(메모리 보호).

## 6. 오류와 예외

| 상황 | 응답 |
|---|---|
| 지원 범위 밖 사고 | 422 `out_of_scope` (기존과 동일) |
| 없는/만료된 세션 | 404 `session_not_found` (둘을 구분해 알려 주지 않는다) |
| 이미 답변한 세션 | 409 `already_answered` |
| 보기 id 범위 밖 | 422 `invalid_option` |
| 질문 생성 실패 | 질문 없이 `done` (실패 사실은 내부 로그에만) |

## 7. 남는 위험과 한계

- **같은 정황으로 새 세션을 여러 번 시작해 보기마다 결과를 보는 것**은 막지 못한다. 질문 순서는 세션마다 바뀌고 결과는 답변 뒤에만 나오지만, 성실히 시도하면 모든 경우의 결과를 알 수 있다. 완화: IP별 호출 제한, 같은 입력 반복 감지는 후속 과제.
- 답변은 진술일 뿐 검증하지 않는다. 결과에는 항상 "사용자 진술 기준"과 필요한 증거 안내를 붙인다.
- 질문이 안 나오는 사고(위원 전원이 같은 가정을 확신)는 질문 없이 결과가 나간다 — `other_possibilities`와 `uncertain`으로만 알린다.
- 응답 시간이 40~130초라 동기 호출은 부적합할 수 있다. 1차는 동기, 이후 작업 큐 + 폴링/SSE (FR-10 실시간 공방 뷰와 함께 설계).

## 8. 결정 사항 (2026-10-15 추천안으로 확정)

1. **답변 반영 방식**: (A) 지금 구현된 `resolve()` — 질문 계획이 계산한 값을 그대로 쓴다. 추가 비용 없음, 위원 검토를 다시 거치지 않는다. (B) 답변을 정황에 덧붙여 **파이프라인을 다시 실행** — 위원 3명이 확정된 사실로 재검토, 건당 약 0.15달러(추정)와 40~130초가 더 든다. 추천: 1차 A, 평가에서 A의 값이 위원 재검토 값과 얼마나 다른지 확인한 뒤 B 여부 결정.
2. **세션 보관**: 메모리+TTL(권장) vs 다른 방식.
3. **내부 `/assess`**: 설정(`INTERNAL_API_ENABLED`)으로 끄는 방식 vs 경로 분리(`/internal/assess`)와 키 인증.
4. 프론트엔드(`frontend/index.html`)가 현재 `/assess`를 직접 쓰므로 `/v1/assess` 흐름으로 바꿔야 한다 (이슈 #14, #15).
